# FEEDBACK

A list of problems with the documentation or workflow, noted by agents (or humans), each with constructive criticism on how it could have been prevented. This is how the conventions improve instead of rotting: when an agent makes a mistake that better instructions would have prevented, the mistake gets an entry here, and a periodic review turns recurring entries into new rules.

Entry format: date, what went wrong (or what friction occurred), and — where possible — a concrete suggestion: which file should say what, so the next agent doesn't hit the same problem.

---

- **26-11-16, Claude Opus 5.5 — judged a tool's limits from the connectors loaded in one session.** In `convos/julian/26-11-16_public_research_log_LOG.md`, I told Julian that "one Google Doc" couldn't be maintained by agents. The Google Drive connector can't edit an existing doc, but the google-workspace skill (which I hadn't loaded yet) says a separate Google Docs connector can. That pushed my recommendation toward a worse option. Suggestion: when judging whether a tool or service can do something, load the matching skill or tool guide first. Report a limit as "not possible with the connectors enabled in this session", not "not possible".

- **26-11-16, Claude Fable 5.2 — prior-work search came last in a project-idea assessment.** In `convos/julian/26-11-16_rlvr_instrumental_convergence_LOG.md`, I had most of a feasibility analysis worked out before a web search showed that the core experiment was published three weeks earlier (arXiv 2610.31624). The find changed the recommendation. Suggestion: CLAUDE.md §Communication Protocol could say that when assessing a research idea, the prior-work search comes first, before feasibility and design work.

- **26-11-16, Claude Fable 5.2 — request file with a non-convention name.** Julian started the topic in `convos/julian/brainstorm.md`. `docs/HOW_TO_USE.md` tells users to name the file `{date}_{topic}_LOG.md`, but CLAUDE.md doesn't tell agents what to do when they don't. I renamed the file and said so in the LOG and in chat. Suggestion: add one line to CLAUDE.md §The Memory System: "If the user's request file doesn't follow the naming convention, rename it to `{date}_{topic}_LOG.md`, keep their text unchanged at the top, and tell them."

- **26-11-18, Claude Opus 5.5 — hand-computed cells in a scripted cost table.** In `convos/julian/26-11-16_rlvr_instrumental_convergence_LOG.md` (answer to "What options do I have to run Olmo?"), a script computed the token volumes and judge costs, but I filled in the GPU-cost cells by hand. Four of them didn't match the stated assumptions. I caught them on a re-check, before Julian read the table. Separately, aggregator sites still listed a hosted Olmo endpoint that the provider's live API no longer had. Suggestion: CLAUDE.md §Quantitative Claims could add two lines. (1) "When a table derives numbers from stated assumptions, compute every cell in one script and keep the script's output next to the table." (2) "For availability and pricing claims, prefer the provider's live API over aggregator pages; aggregators go stale."

- **26-11-18, Claude Opus 5.5 — `git mv` / `git rm --cached` while restructuring code.** Moving `src/ic_eval/vast.py` into a package (`convos/julian/26-11-18_vast_host_selection_LOG.md`, entry *implementation, simulation findings, backfilled history*), I used `git mv` out of habit. That changes git's index, and CLAUDE.md forbids any git state change by agents. I noticed it from `git status`, restored the index for exactly those paths with `git restore --staged`, and left Julian's own staged entries alone. Suggestion: CLAUDE.md §"API keys and git" could name the commands that look harmless: "this includes `git mv`, `git rm`, `git add` and `git restore --staged`; move files with plain `mv`".
- **26-11-18, Claude Opus 5.5 — wrote a placeholder test with a meaningless assertion.** In the same entry, my first simulation test compared against an empty list and asserted a trivially true value. I replaced it before running the suite. That broke CLAUDE.md's "no placeholders" rule, and the replacement found a real design issue (exploration valued time at the wrong rate). Suggestion: `docs/CODING.md` §Testing could add: "Before writing a test, write down the comparison that would fail if the code were wrong; if there isn't one yet, don't write the test."

- **26-11-18, Claude Opus 5.5 — boot code tested only on hand-picked message fragments, so the first live run crashed.** In `convos/julian/26-11-18_vast_host_selection_LOG.md` (entry *live test 1: two boot bugs fixed, staircase pull progress found*), the first rental crashed in the boot loop: the first pull message arrived in the first poll, and a prediction was computed with 0 s elapsed. A second bug had the same cause: the pull-end detector knew only BuildKit lines. A third flaw, "done" bytes moving in big steps, only showed when the whole sequence of real status messages was watched. The parser tests used individual real messages, as `docs/CODING.md` §Testing asks, but nothing drove the loop with a whole real sequence, including timing. Every attempt in `rentals.jsonl` keeps its full poll list, so such sequences were available. Suggestion: `docs/CODING.md` §Testing could add: "For code that consumes a stream (polls, logs), also test it end to end on whole recorded sequences, with their timestamps, replayed through a fake clock; the first and last few events are where it breaks."

- **26-11-23, Claude Opus 5.5 — built variants one request at a time without an overall design, so the code turned janky.** In `convos/julian/26-11-22_bluedot_course_exercises_LOG.md` I implemented a dataset option, then split it into two task files, then moved paths into them, then designed parsers with thresholds inside the judge task, each step in direct response to Julian's latest message. Julian had to stop and ask for the overall design; it showed that tasks should be per procedure (not per setting) and that interpretation (parsing, thresholds) belongs in analysis, which reverses two of those steps. Suggestion: `docs/CODING.md` could add: "Before adding a second variant of a component (a second task, a second data format), write down in the LOG what varies, where each varying thing is set and where it is recorded. If a variant can be a parameter recorded by the tool (here: Inspect's log header), make it a parameter."
